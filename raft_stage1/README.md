# Raft, этап 1: каркас узла, выбор лидера и REST status

Этот каталог содержит самостоятельную учебную реализацию первого этапа Raft на
Python 3. В ней есть кластер из фиксированного набора узлов, роли
`follower/candidate/leader`, сроки (terms), выборы по большинству, heartbeat,
переизбрание после отказа лидера, сохранение обязательного состояния на диск и
REST API для наблюдения.

Репликации журнала, применения команд и key-value хранилища здесь намеренно нет:
это следующие этапы задания. Поля журнала уже присутствуют в RPC и status, но
пока имеют начальное значение `0`.

## Быстрый запуск кластера

Зависимости устанавливать не нужно: используется только стандартная библиотека
Python 3.10 или новее.

Из корня репозитория откройте три терминала.

Терминал 1:

```powershell
python -m raft_stage1 --config raft_stage1/configs/node1.json
```

Терминал 2:

```powershell
python -m raft_stage1 --config raft_stage1/configs/node2.json
```

Терминал 3:

```powershell
python -m raft_stage1 --config raft_stage1/configs/node3.json
```

Через 1.5-3 секунды один процесс напечатает `becomes leader`. Проверить все узлы
можно из PowerShell:

Во время выборов консоль показывает весь обмен голосами. Например:

```text
node2: начинает выборы term=1 и голосует за себя
node2: просит node1 проголосовать за node2 в term=1
node1: получил запрос голоса от node2, кандидат просит голос за себя в term=1
node1: голосует за node2 в term=1
node2: node1 проголосовал за node2 в term=1
```

При отказе выводится причина: устаревший term, уже отданный другому кандидату
голос или отстающий журнал.

```powershell
Invoke-RestMethod http://127.0.0.1:8101/status
Invoke-RestMethod http://127.0.0.1:8102/status
Invoke-RestMethod http://127.0.0.1:8103/status
```

Или через `curl`:

```bash
curl http://127.0.0.1:8101/status
```

У одного узла будет `"role": "leader"`, у двух остальных -
`"role": "follower"`; у всех должен совпасть `term`, а `leader_id` должен
указывать на выбранного лидера.

Чтобы увидеть переизбрание, остановите лидера сочетанием `Ctrl+C`. Оставшиеся два
узла составляют большинство исходного кластера из трёх, поэтому через новый
таймаут один из них станет лидером следующего срока. Один оставшийся узел не смог
бы избрать лидера: для кластера из трёх нужен кворум `2`.

## Конфигурация

Пример `node1.json`:

```json
{
  "id": "node1",
  "host": "127.0.0.1",
  "port": 8101,
  "peers": {
    "node2": "http://127.0.0.1:8102",
    "node3": "http://127.0.0.1:8103"
  },
  "data_dir": "../../.raft-data/node1",
  "election_timeout_min": 1.5,
  "election_timeout_max": 3.0,
  "heartbeat_interval": 0.5,
  "rpc_timeout": 0.7
}
```

Поля:

- `id` - уникальный логический идентификатор узла;
- `host`, `port` - адрес его HTTP-сервера;
- `peers` - все остальные узлы фиксированной конфигурации кластера;
- `data_dir` - каталог устойчивого состояния; относительный путь считается от
  файла конфигурации;
- `election_timeout_min/max` - диапазон случайного таймаута выборов;
- `heartbeat_interval` - период heartbeat лидера;
- `rpc_timeout` - сетевой таймаут одного RPC.

На каждом узле список участников должен описывать один и тот же кластер. Сам узел
в `peers` не добавляется. Частота heartbeat обязана быть выше частоты возможных
выборов, поэтому `heartbeat_interval < election_timeout_min` проверяется при
старте.

Данные трёх примеров попадают в `.raft-data/node1`, `.raft-data/node2` и
`.raft-data/node3`. Если нужно начать эксперимент с полностью чистого состояния,
сначала остановите все процессы, затем удалите эти три каталога вручную. При
обычном перезапуске удалять их нельзя: сохранение срока и голоса является частью
гарантий Raft.

## REST API

### `GET /status`

Публичный диагностический endpoint. Пример сокращённого ответа:

```json
{
  "node_id": "node2",
  "role": "leader",
  "term": 3,
  "leader_id": "node2",
  "voted_for": "node2",
  "cluster_size": 3,
  "quorum": 2,
  "running": true,
  "election_timeout_remaining_seconds": null,
  "last_leader_contact_age_seconds": null,
  "log": {
    "last_index": 0,
    "last_term": 0,
    "commit_index": 0,
    "stage": "not implemented until step 2"
  },
  "stats": {
    "elections_started": 1,
    "leaderships_started": 1,
    "heartbeats_sent": 12,
    "heartbeats_received": 0,
    "rpc_errors": 0
  }
}
```

У лидера оставшийся election timeout равен `null`: лидер сам выборов не запускает.
У follower это число показывает, сколько примерно осталось до новых выборов без
следующего heartbeat.

### `GET /health`

Проверяет доступность HTTP-процесса:

```json
{"status": "ok", "node_id": "node1"}
```

Это liveness-проверка, а не доказательство наличия кворума или лидера. Для
диагностики кластера нужен `/status` нескольких узлов.

### Внутренние RPC

Узлы общаются через два JSON/HTTP вызова:

- `POST /raft/request-vote` - запрос голоса кандидатом;
- `POST /raft/append-entries` - heartbeat лидера. В первом этапе `entries` всегда
  пуст; во втором этот же RPC будет переносить элементы журнала.

Они открыты только для демонстрации и тестов. Это не клиентское API и в
production-системе должно быть защищено взаимной аутентификацией и TLS.

Запрос голоса:

```json
{
  "term": 4,
  "candidate_id": "node2",
  "last_log_index": 0,
  "last_log_term": 0
}
```

Ответ:

```json
{"term": 4, "vote_granted": true}
```

Heartbeat (`AppendEntries` без записей):

```json
{
  "term": 4,
  "leader_id": "node2",
  "prev_log_index": 0,
  "prev_log_term": 0,
  "entries": [],
  "leader_commit": 0
}
```

Ответ:

```json
{"term": 4, "success": true, "match_index": 0}
```

## Как Raft работает в этой реализации

### 1. Роли и сроки

Каждый узел всегда находится в одной из трёх ролей:

| Роль | Что делает |
| --- | --- |
| `follower` | Ждёт heartbeat лидера и отвечает на RPC. |
| `candidate` | Запустил новый срок, голосует за себя и собирает голоса. |
| `leader` | Регулярно отправляет heartbeat всем follower. |

`term` - монотонно растущие логические часы. Номер увеличивается не по реальному
времени, а при начале новых выборов. В каждом сообщении передаётся term. Узел,
увидевший больший term, немедленно принимает его и становится follower. Поэтому
старый лидер после разделения сети не сможет продолжить руководить, когда снова
встретится с узлом из более нового срока.

### 2. Начальное состояние

При запуске узел читает `data_dir/state.json`. Там находятся:

- `current_term` - последний известный срок;
- `voted_for` - кому узел уже отдал голос в этом сроке, либо `null`.

Эти два поля Raft требует хранить устойчиво. Файл записывается до отправки
положительного ответа на голосование и заменяется атомарно. После рестарта узел не
сможет забыть выданный голос и проголосовать в том же сроке второй раз.

Остальное состояние (`role`, известный лидер, дедлайны, статистика) временное.
После запуска узел всегда follower и устанавливает случайный election timeout.

### 3. Почему election timeout случайный

Если все follower одновременно перестанут видеть лидера и одновременно станут
candidate, каждый успеет проголосовать за себя. В кластере из трёх получится три
кандидата по одному голосу - `split vote`.

Каждый узел выбирает срок ожидания случайно из диапазона 1.5-3.0 секунды. Обычно
первым просыпается один кандидат, получает голоса ещё до таймаутов остальных и
побеждает. Если голоса всё же разделились, кандидат по следующему случайному
таймауту увеличит term и повторит попытку.

Практическое соотношение времён должно быть таким:

```text
время рассылки RPC << election timeout << среднее время между отказами
```

Слишком короткий election timeout вызывает ложные выборы при обычной задержке
сети; слишком длинный увеличивает время восстановления после отказа.

### 4. Начало выборов

Когда follower или candidate не получает heartbeat до своего дедлайна, он:

1. увеличивает `current_term`;
2. становится candidate;
3. устойчиво записывает голос за себя;
4. создаёт множество голосов `{self}`;
5. выбирает новый случайный дедлайн повторных выборов;
6. параллельно посылает `RequestVote` всем peers.

Для `N` узлов кворум вычисляется как `floor(N / 2) + 1`. Это не половина, а строгое
большинство: 1 из 1, 2 из 3, 3 из 5, 4 из 6.

### 5. Выдача голоса

Получатель `RequestVote` действует в следующем порядке:

1. Если term запроса меньше локального, отвечает отказом и своим новым term.
2. Если term больше, переходит в него, очищает старый голос и становится follower.
3. Проверяет, что в этом term ещё не голосовал либо уже голосовал за того же
   кандидата. Повторный одинаковый RPC поэтому идемпотентен.
4. Проверяет актуальность журнала кандидата по паре
   `(last_log_term, last_log_index)`.
5. При успехе устойчиво записывает голос, сбрасывает election timeout и только
   потом отвечает `vote_granted: true`.

На первом этапе журналы пусты, поэтому у всех `(last_log_term, last_log_index)`
равно `(0, 0)`. Проверка уже реализована, чтобы второй этап не менял правила
выборов: после появления записей преимущество получит кандидат с более свежим
журналом.

### 6. Победа кандидата

Candidate учитывает только ответы, которые относятся к его текущему сроку. Как
только вместе с собственным голосом набрано большинство, он становится leader и
сразу планирует первый heartbeat.

Пересечение любых двух большинств содержит хотя бы один общий узел. Поскольку
узел устойчиво голосует максимум за одного кандидата в term, два разных
кандидата не могут честно собрать большинство в одном term. Это свойство называют
Election Safety.

### 7. Heartbeat и удержание лидерства

Leader каждые 0.5 секунды отправляет всем узлам `AppendEntries` с пустым массивом
`entries`. Follower с подходящим term:

- принимает отправителя как текущего лидера;
- переходит из candidate в follower, если сам начал выборы;
- сбрасывает election timeout;
- отвечает своим term.

Heartbeat не является отдельным RPC Raft: это обычный `AppendEntries` без новых
элементов. Благодаря этому второй этап добавит репликацию в уже существующий
канал.

Leader не считает неудачу одного heartbeat поводом немедленно отказаться от роли.
В Raft лидер обнаруживает потерю авторитета косвенно: он либо увидит ответ с
большим term и станет follower, либо не сможет подтвердить новые записи
большинством (эта часть появится на втором этапе).

### 8. Отказ лидера и переизбрание

После падения лидера heartbeat прекращаются. У каждого follower свой дедлайн;
первый истёкший узел запускает следующий term. Если он доступен большинству, то
собирает кворум и становится новым лидером.

Старый лидер при возвращении может некоторое время считать себя leader своего
старого term. Первый RPC или ответ от нового срока содержит больший term, после
чего старый лидер становится follower. До реализации журнала клиентских команд у
него всё равно нет возможности подтвердить изменение состояния.

### 9. Сбои и особенности сети

Статья моделирует ненадёжную сеть, где сообщения могут теряться, дублироваться и
приходить в другом порядке. Здесь HTTP работает поверх TCP, но соединение всё
равно может завершиться ошибкой или таймаутом. Алгоритм не зависит от доставки
каждого отдельного RPC:

- повторный голос тому же кандидату в том же term безопасен;
- повторный heartbeat безопасен;
- сообщение старого term отвергается;
- ответ нового term заставляет отправителя перейти в follower;
- потерянный heartbeat заменяется следующим, пока несколько потерь подряд не
  превысят election timeout.

В отличие от сокращённой LNT-модели из статьи, реализация отвечает на устаревший
RPC текущим term. Это помогает отставшему отправителю быстрее обнаружить новый
срок. Число узлов фиксировано конфигурацией, но число сроков не ограничено.

## Потоки и синхронизация

В одном процессе работают:

- HTTP-сервер с отдельным потоком на входящий запрос;
- один timer-поток, следящий за election timeout и heartbeat;
- небольшой пул исходящих RPC.

Все переходы роли, срока и голоса защищены `RLock`. Сетевой запрос не выполняется
под этой блокировкой: иначе медленный peer остановил бы обработку heartbeat и
голосов. Ответ применяется только после повторной проверки роли и term, поэтому
запоздалый ответ от предыдущих выборов не может сделать узел лидером.

```text

  api.py           HTTP-сервер, status/health и входящие RPC

  node.py          роли, таймеры, выборы, heartbeat и обработчики RPC
  storage.py       атомарное хранение current_term и voted_for

```

## Проверка тестами

```powershell
python -m unittest -v test_raft_stage1.py
```

Первый тест доказывает, что узел не отдаёт два голоса в одном term и помнит голос
после создания нового объекта из того же `data_dir`. Второй поднимает три реальных
HTTP-сервера, ждёт лидера, проверяет `/status`, останавливает лидера и ждёт лидера
следующего срока среди двух выживших.

## Что гарантируется, а что пока нет

На первом этапе реализованы:

- не более одного голоса узла в одном term, включая рестарт;
- выбор лидера только большинством;
- переход в follower при большем term;
- автоматическое переизбрание при доступном кворуме;
- устойчивость к потерянным, повторным и запоздавшим election/heartbeat RPC;
- наблюдаемое состояние через REST.

Пока не реализованы:

- журнал и его репликация;
- commit index и применение команд к state machine;
- клиентские операции и перенаправление на лидера;
- snapshot/compaction;
- динамическое изменение состава кластера;
- аутентификация, TLS, rate limiting и защита от злонамеренного узла;
- production-механизмы вроде pre-vote, check-quorum и leadership transfer.

Поэтому это корректный учебный первый этап, но не готовый production consensus
service.

## Как продолжить вторым этапом

Для `Репликация лога + add entries/show log` нужно будет:

1. добавить устойчивый список записей `(term, command)`;
2. хранить `commit_index` и `last_applied`;
3. при становлении лидером создать для каждого follower `next_index` и
   `match_index`;
4. отправлять через существующий `AppendEntries` нужный хвост журнала;
5. проверять `prev_log_index/prev_log_term`, удалять конфликтующий хвост и
   дописывать записи;
6. считать запись committed после репликации большинством, причём для безопасного
   продвижения commit index учитывать term записи;
7. добавить клиентский REST endpoint для записи и диагностический endpoint для
   просмотра журнала.

Главное: правила выбора лидера уже учитывают последние term/index журнала, а
формат `AppendEntries` уже содержит поля второго этапа. Поэтому расширение не
потребует переделывать протокол первого этапа.
